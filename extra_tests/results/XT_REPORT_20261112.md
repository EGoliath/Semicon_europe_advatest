## Verdict per principle

- **Bit packing + transpose (`pp`)** is what makes the difference: 1.74x smaller than zstd -9 with the same backend.
- **`--long=31` really pays only on the bit planes** (`pp:zstd9` → `pp:zstd9L`: 997.8 → 777.3 MB, -22%).
  The long window finds the duplicate pins (38% of pins) across the whole plane stream with no explicit dedup.
  On raw bytes it gains only 4%.
- **Byte transpose alone (`tr8`)** gains little with the default zstd window (1.11x). With `--long` it reaches 1.52x, still far below `pp`.
- **BWT (bzip3)**: confirmed it "bypasses the transpose": `raw:bz3` (913.8 MB) ≈ `tr8:bz3` (902.4 MB).
  On `pp` it gives 840.4 MB, but compression and decompression are both ~200 MB/s, so it loses to `pp:zstd9L` on all three axes.
- **XOR between rows (`rx`)** is worse than per-pin planes (1069.7 vs 777.3 MB). **Bit transitions (`ppd`)** are
  slightly worse than plain `pp` (+2.7%). Both are rejected, which matches the earlier measurement.
- **RAP 16 MiB frames + OpenMP decode**: no size cost here (the zstd-9 window is 8 MiB anyway).
  Decode of raw zstd goes 1211 → 4776 MB/s (3.9x). On `pp` the zstd stream is already small, so the gain is 1810 → 2114.
- **LZ4 / LZ4HC, deflate, brotli on `pp`**: all lose to `pp:zstd9L` on size. LZ4 has the fastest compression (2318 MB/s) but is 1.9x bigger.

The new configs match the earlier `planes` sizes with much simpler code (no explicit pin dedup, because the long window
does it). Decoding is 2–3x faster in this bench, but this bench decodes in memory into huge pages and does no file I/O,
so that speed gap is partly the harness. A same-harness comparison is still needed before claiming the speed-up.
